# LinuxDevStackBox - Architecture Overview

**Architecture baseline**: v0.1.25 (October 2026). For current project/PHP/HTTPS behavior, see [Projects, PHP & HTTPS](../getting-started/projects) and [Feature status](../feature-status).
**Single Source of Truth**: This file describes how all parts of LinuxDevStackBox connect. Update this file whenever you change the architecture.

## UI Layout

LinuxDevStackBox uses a fixed two-panel desktop app layout. Do not redesign this.

```text
┌───────────────────┬──────────────────────────────────────┐
│  Top Bar          │  Top Bar (continued)                 │
│  LinuxDevStackBox      │  [Version] [Updates] [Lang] [Theme]  │
├───────────────────┼──────────────────────────────────────┤
│                   │                                      │
│  Sidebar          │  Main Content Area                   │
│  (220-260px)      │                                      │
│                   │  Current Page:                       │
│  Dashboard        │  Service cards / logs / settings     │
│  Services         │  Config editor / PHP versions        │
│  Projects         │                                      │
│  Logs             │  Clean, spacious, card-based.        │
│  Settings         │                                      │
│  About            │  NO crowded tables.                  │
│                   │                                      │
└───────────────────┴──────────────────────────────────────┘
```

**Top Bar currently contains:**

- App title
- Version badge
- Update check entry point
- Language switcher
- Theme toggle (dark/light)

**Current shortcut-driven controls:**

- Command palette opens with `Ctrl+P`
- Tray controls exist in dedicated components and hooks, but are not mounted in the current top bar

**Sidebar currently contains:**
`Dashboard` / `Services` (Apache / MySQL / PHP sub-navigation) / `Databases` / `Logs` / `Terminal` / `Settings` / `About`

All sidebar items are active. Each service has its own sub-pages: Overview, Logs, Config, and service-specific extras (PHP: Extensions, Versions; Apache: Virtual Hosts, SSL).

Do not overload the sidebar with sub-items or collapsible trees.

**Dashboard page structure:**

```text
Dashboard
├── Quick Actions (Start All / Stop All / Restart Apache)
├── Service Status Cards (Apache / PHP / MySQL)
├── Current PHP Version
├── Ports Overview
├── Recent Logs (last 10 lines)
└── Project Shortcuts (www/ folder links)
```

**Service card structure (each card):**

```text
[ Apache ]       Running ●
Port: 8080   PID: 1234
[ Start ]  [ Stop ]  [ Logs ]  [ Config ]
```

**Progressive Disclosure Rule:**  
Default view shows: start / stop / running status only.  
Expanded view shows: logs, config, ports, PID, arguments.  
This keeps the UI approachable for beginners, powerful for advanced users.

**Design Philosophy:**  
LinuxDevStackBox should feel like a native desktop utility (like Docker Desktop or GitHub Desktop), NOT like a web admin panel, analytics dashboard, or cPanel.

## Reuse and Consistency Rules

These rules are architectural, not optional style preferences.

1. Reuse existing shared components before creating new ones. Start with `ServiceCard`, `ServiceActions`, `StatusBadge`, `LogViewer`, `ConfigEditor`, and existing shadcn/ui primitives.
2. Keep business logic in one owner. Polling stays in `service-manager.tsx`; command strings stay in `src/lib/commands.ts`; shared types stay in `src/types/services.ts`.
3. Prefer composition over cloning. If two screens need the same card, toolbar, or dialog shell, add props or children to the shared component instead of copying markup.
4. Keep visual language consistent. The same action should use the same component, label pattern, spacing scale, and variant wherever it appears.
5. If a new reusable pattern is introduced, document it in `development/components` immediately so future work can extend it instead of recreating it.

## App/Data Directory Separation

LinuxDevStackBox separates packaged application files from per-user state following the XDG Base Directory Specification. Packages install the binary and static resources under `/usr/bin/linuxdevstackbox` and `/usr/lib/linuxdevstackbox/` (replaced by package upgrades); all mutable user state lives under the XDG roots (never touched by package operations):

- **Config root**: `$XDG_CONFIG_HOME/linuxdevstackbox` (default `~/.config/linuxdevstackbox`) - generated `httpd.conf`, `my.cnf`, `php.ini`, `vhosts.json`, HTTPS material and the 0600 MySQL root credentials file.
- **Data root**: `$XDG_DATA_HOME/linuxdevstackbox` (default `~/.local/share/linuxdevstackbox`) - `logs/`, `mysql-data/`, `www/`, `backups/`, `config-backups/`, the writable phpMyAdmin copy and the staged `cgi-bin/`.

Both roots can be relocated together with the `LINUXDEVSTACKBOX_DATA_DIR` environment variable. Connected projects can also live outside these roots entirely. Never replace or delete the user roots during an upgrade.

This is critical for reliable package upgrades. Violating this causes update-related data loss. See [Configuration](../reference/configuration) for preservation limits.

## How Frontend Talks to Rust (IPC Pattern)

Every call from React to Rust goes through `src/lib/tauri.ts:safeInvoke()`.

```text
React Component
  --> safeInvoke("command_name", { param: value })   [src/lib/tauri.ts]
      --> Tauri invoke()                             [Tauri IPC bridge]
          --> #[tauri::command] fn command_name()   [src-tauri/src/lib.rs]
              --> Result<T, String>                 [returned to frontend]
```

**Rules:**

- Always use `safeInvoke` (not raw `invoke`) so it works in browser dev mode too
- Shared command names live in `src/lib/commands.ts:TAURI_COMMANDS`; expand that file instead of creating new scattered constants
- Current gap: some older components still hardcode command strings and should be migrated into `TAURI_COMMANDS`
- All commands are in `src-tauri/src/lib.rs` - do NOT use `service_manager.rs`
- Commands return `Result<T, String>` - errors are caught in the component

## How Rust Talks Back to Frontend (Events)

For real-time data (log streaming, service status changes), Rust uses Tauri events:

```text
Rust (lib.rs)
  --> app_handle.emit("event-name", payload)
      --> Frontend listener
          --> listen("event-name", callback)         [Tauri event API]
```

This pattern is used for progress and app-shell events such as full backup/restore progress, terminal output, and tray actions. Service status and log refresh still use frontend polling for now.

## Service Path Resolution

This is a critical and error-prone area. Path helpers live in `src-tauri/src/utils/paths.rs`.

`get_installation_path()` resolves where static application assets (the phpMyAdmin runtime payload, templates) live:

1. Debug builds: the repository root
2. Release builds: the directory next to the executable, then `/usr/lib/linuxdevstackbox` (package installs), selected by whichever contains `phpmyadmin/`

Server binaries are never bundled. Apache (`httpd` or `apache2`), MySQL/MariaDB (`mysqld` or `mariadbd`, clients `mysql`/`mariadb`, `mysqldump`/`mariadb-dump`, `mysqladmin`/`mariadb-admin`), PHP (`php`, `php-cgi`, minimum 8.2) and `openssl` are resolved from the distribution packages. The Apache modules directory and `mime.types` are derived from `httpd -V` (`HTTPD_ROOT`), so both httpd-based and apache2-based layouts work.

User state uses two XDG roots (see App/Data Directory Separation above), both overridable with `LINUXDEVSTACKBOX_DATA_DIR`.

**Rule:** Never hardcode paths in the frontend. Always let the Rust backend resolve paths.

## Process Ownership and Privilege Separation

- Service processes are detected by scanning `/proc`; a process counts as "ours" only when its command line references the app's generated config (`httpd.conf` / `my.cnf`). System services that happen to run the same binaries are never touched.
- Started services run in their own process groups. Stop is graceful first (`httpd -k stop` / `mysqladmin shutdown`), then SIGTERM, then SIGKILL.
- The GUI never runs as root. Exactly two operations are elevated, each a single fixed-argument `pkexec` invocation of the app binary itself:
  - `--hosts-operation add|remove <domain>` - edits `/etc/hosts`
  - `--ca-trust-operation install|remove` - installs or removes the local CA anchor in the distro trust store and refreshes it
- Other CLI flags: `--setup-local-https`, `--https-status`, `--start-apache`, `--stop-services`.

## State Management

`src/lib/workspace-cache.ts` and `use-workspace-query.ts` share in-memory snapshots, deduplicate requests and reject outdated results. Project/database mutations invalidate related keys. Visible screens refresh on bounded intervals; hidden windows suspend polling. These caches improve navigation, not process truth or credential storage.


There is no global state manager (no Redux, Zustand, etc.). State is managed:

- **Local component state**: `useState` in each page/component
- **Service status polling**: `ServiceManager` component polls every 5 seconds via `safeInvoke`
- **Theme**: React context via `ThemeProvider`
- **Rust-side state**: Runtime process truth comes from OS process checks, not a service status cache. Terminal sessions and other command-specific state stay inside their owning backend modules.

**Rule:** Do not add a global state manager unless shared state between 3+ unrelated components becomes unmanageable.

## Build Pipeline

```text
npm run build:release
  --> npm run build (tsc && vite build)  --> dist/
  --> cargo build --release              --> src-tauri/target/release/
  --> tauri bundle                       --> .deb and .rpm packages
```

Resources bundled into the packages are declared in `tauri.conf.json`:

```json
"resources": {
  "../packaging/phpmyadmin-runtime": "phpmyadmin"
}
```

Arch packaging does not use the Tauri bundler; it builds from source via `packaging/arch/PKGBUILD` and installs the same phpMyAdmin payload under `/usr/lib/linuxdevstackbox/phpmyadmin`.

## Adding a New Feature: Checklist

1. **Rust backend command** (if needed): Add `#[tauri::command] async fn my_command()` to the owning module in `src-tauri/src/commands/`, then register it in the `invoke_handler` in `src-tauri/src/lib.rs`.
2. **Frontend constant**: Add the command name to `TAURI_COMMANDS` in `src/lib/commands.ts`.
3. **TypeScript types**: Add any new types to `src/types/services.ts`.
4. **React component**: Create component in appropriate folder. Style with Tailwind + shadcn/ui only.
5. **Translation keys**: Add EN and HI strings to `locales/en.json` and `locales/hi.json`.
6. **Update this doc**: Update development/architecture and feature-status.

## Key Design Decisions

| Decision                                | Reason                                                                          |
| --------------------------------------- | ------------------------------------------------------------------------------- |
| Commands split by domain                | Keeps `lib.rs` small and places service logic in `src-tauri/src/commands/`      |
| `safeInvoke` wrapper                    | Allows frontend to run in browser during development                            |
| No custom CSS                           | Tailwind + shadcn/ui covers all needs; custom CSS causes theming bugs           |
| Polling for service status              | Simple and reliable for current service cards; events are used for progress flows |
| XDG config/data roots                   | Keeps per-user state separate from package-managed files and follows Linux conventions |
| `config-backups/` auto-backup           | Auto-backup before every config save prevents data loss                         |
| Two-panel layout (sidebar + main)       | Standard desktop utility pattern; do not redesign                               |
| Progressive disclosure in service UI    | Beginners see start/stop; experts expand for logs, config, PID                  |
| App/data directory separation           | Required for safe package upgrades; see reference/installer                     |
| Distro packages for server binaries     | No bundled servers: smaller packages, security updates via the package manager  |
| pkexec for the only two elevated ops    | The GUI never runs as root; elevation is a single fixed-argument invocation     |


## Database operation layer

`commands/database_workspace.rs` owns native operation records and sequential worker execution. `DatabaseOperationsProvider` polls the native registry so route changes do not discard progress. The process-local database guard coordinates imports, exports, account/schema mutations and MySQL stop operations. Native window/tray close paths refuse ordinary app exit during active operations; this does not promise crash survival or automatic resume.

`utils/database_io.rs` keeps sensitive SQL on stdin and publishes backup files only after successful process/file completion. The SQL connection sets a known literal-escaping mode for generated statements. Imported dumps keep their own SQL semantics. ZIP imports use a versioned manifest, strict entry validation, expanded-size limits and checksums before executing SQL. Backup integrity is distinct from restore verification.

Database metadata is cached in memory, invalidated when the observed MySQL port changes, and older requests cannot overwrite newer refresh results. Persistent operation history is bounded to 50 entries and unfinished jobs are marked interrupted after restart. This is a local operation log, not a distributed transaction coordinator.

## Log management

`commands/log_management.rs` owns managed-file validation, archive integrity and shared rotation/retention. `use-log-stream.ts` reads bounded incremental tails and pauses background polling. Clear view advances a view cursor; archive/delete are separate filesystem operations. Service writers must stop before archival.

The build stages phpMyAdmin using `scripts/stage-phpmyadmin.mjs` into `packaging/phpmyadmin-runtime`; the packages ship that read-only payload, and the app clones it into the user data root on first run because `config.inc.php` must be writable.
