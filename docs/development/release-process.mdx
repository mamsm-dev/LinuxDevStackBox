# v0.1.22 release process

The source version is 0.1.22. Package generation, installed qualification and publication are separate steps. [Release runbook](./release-runbook) contains the exact commands.

## 1. Review source and versions

- Review the app and website changes and the changelog.
- Match package.json, src-tauri/Cargo.toml and src-tauri/tauri.conf.json at 0.1.22; synchronize app entries in both lockfiles (package-lock.json and Cargo.lock).
- Run npm run check, `npm run test:packaging`, Rust unit tests and both Apache regression modes.
- Preserve historical release notes and hashes. Generated download manifests stay associated with their original assets until finalization.

## 2. Build the packages

Build the `.deb` and `.rpm` bundles with `npx tauri build --bundles deb rpm` as described in the runbook (the bundle targets are configured in src-tauri/tauri.conf.json). The Arch package is built separately from `packaging/arch/PKGBUILD` with `makepkg -f`. There is no code-signing step; never bypass a failed integrity or checksum check.

## 3. Finalize from the exact artifact

Confirm the published packages and release metadata all describe the same bytes: same version, matching checksums, release notes and changelog hash. Do not use a previous build's checksum or invent a download URL for an unavailable release.

## 4. Qualify on Linux

- Test a fresh install and an upgrade on a clean environment for each supported distro family (Arch, Debian, Fedora), with project/database backups.
- Verify custom ports, user PHP settings, site records and database contents survive.
- Verify the Apache migration creates its backup and does not duplicate the baseline after restart.
- Verify Laravel public-directory routes, static assets, HTTP and HTTPS, and a project with parent .htaccess. Check that private parent files remain inaccessible.
- Verify plain PHP and a root-level rewrite project; the distro PHP version is respected (minimum 8.2).
- Compare the displayed log path with the running server configuration and confirm a fresh request is observable.
- Check localhost, phpMyAdmin, large SQL restore failure reporting and the update check.

Record actual results and remaining limitations in docs/RELEASE-VALIDATION.md. Do not label unperformed tests as passed. [Testing](./testing) provides details.

## 5. Publish and verify

Commit reviewed source, create the v0.1.22 tag, and upload the `.deb`, `.rpm` and Arch package plus release notes to GitHub Releases. Publish `latest.json` on the release so the in-app update check can detect the new version: the updater is check-only, so on update availability the app opens the release page and instructs the user to upgrade through their package manager (Tauri self-update only supports AppImage, which is not a deliverable). Verify remote assets match the local artifacts and their checksums.

## 6. Website

Commit the source docs before hosted website builds. Pin the app-doc source ref to v0.1.22 or the exact reviewed commit. Run content preparation, website tests, lint, build and HTTP smoke checks. Publish only after download assets are available; release availability is read from GitHub, not inferred from source version. Use approved native-resolution screenshots matching the documentation baseline. Keep capture provenance distinct from release availability.
